# Directive 24 — Parallel Enrichment Capability — Adversarial Assessment

**Reviewer:** adversarial principal-engineer pass · **Date:** 2026-06-04
**Plan under review:** `docs/reference/DIRECTIVE_24_PARALLEL_ENRICHMENT_CAPABILITY.md`
**Grounding:** core-x code (file:line), live trigger.dev docs + MCP, live Parallel docs/OpenAPI, live R2 `data-sink` (Doppler `core-x/prd`), live `companies` Lance manifest.

---

## 1. Overall verdict — **SHIP WITH CHANGES**

The plan is architecturally sound, fits the stated aim (a reusable per-spec enrichment scaffold), and most of its system claims hold up against live verification — including the ones the prompt suspected were wrong (the maxDuration concern is a non-issue; dynamic discovery genuinely auto-surfaces `enrichment/<spec>`; the namespaced name resolves and double-quotes correctly in the audience SQL path; `company_id` is PK-grade). It is not ship-as-is because of **four concrete defects**: (a) the §3/§5.1 topology claims to "mirror exa_websets.ts" but prescribes a poll-via-`wait.for` pattern that **exists nowhere in the repo** — every one of 50 trigger tasks uses `wait.forToken`+Modal-internal-poll, and exa polls *inside Modal*, not via trigger suspend; (b) `companies` has **no `company_website` column** (only `normalized_domain`), so the Parallel `input={company_name, company_website}` shape in §3/§5.1 is unsatisfiable as written; (c) the §4.2 `refresh_catalog()` fix is sufficient only on the happy path — it does not bust `catalog.py`'s `_lance_cache`/`_schema_cache`, so a pre-landing probe poisons the schema until restart; (d) `PARALLEL_API_KEY` is **already in Doppler `core-x/prd`** (§8 wrongly says provision it) while the Modal secret `parallel-api` is genuinely absent. None are architecture-breaking; all are fixable in-place.

## 3. Gaps the plan missed (verified, not speculative)

1. **`company_website` does not exist on `companies` (HIGH).** Live manifest cols: `company_id, company_name, normalized_domain, company_linkedin_url, source_platform`. Plan §3/§5.1 send Parallel `input={company_name, company_website}`. The worker/trigger must derive the URL from `normalized_domain` (e.g. `"https://"+normalized_domain`). The equipment JSONs all anchor on a full website URL — the input contract has to produce one. Unaddressed.
2. **Companies with no website (MEDIUM).** 5/758 rows have null `normalized_domain` → no derivable input. No skip/route rule; they'd produce empty/garbage Parallel runs that still bill. Add a pre-filter (and count it in the run ledger `requested`).
3. **catalog.py cache poisoning + stale `column_count` (MEDIUM).** §2.2 above. `refresh_catalog()` must also clear `catalog._lance_cache` and `catalog._schema_cache` (or expose a `catalog.invalidate()` the tool calls), else a premature `describe_dataset` sticks `None` past refresh and `list_datasets` never shows the spec's column count until restart.
4. **Per-company partial failure inside a group (MEDIUM).** Group status exposes `failed` counts but the plan's landing only describes the success path. Define: land completed rows, write failed `company_id`s to `ops.parallel_runs.failed` (+ optionally a per-company failure ledger), and make re-run target only the missing/failed `company_id`s.
5. **Idempotency key on the trigger run (MEDIUM).** exa_websets sets `externalId`/`externalId`-via-`run_id` to make create idempotent and avoid double credit spend (`exa_websets.ts:91-104,600`); the email-cascade uses `idempotencyKey` on waitpoints. The plan's launch tools have no idempotency key, so a double-fire bills Parallel twice. Mirror the precedent (key off `spec_id`+`audience_id`+`run_kind`).
6. **Array/nested `output_schema` → Lance columns (MEDIUM).** `industries_served` is `array<string>` and `_basis` is nested. The plan says "columns = output_schema fields" but never says how arrays/objects map to Arrow/Lance types or how `<field>__confidence` is derived for an array field (the per-array-element basis header changes basis cardinality). DuckDB can emit `LIST`/`STRUCT` (see `ca_cslb` personnel `LIST<STRUCT>`), but the mapping rule must be explicit in `pipelines/parallel/task_enrich.py`.
7. **output_schema ⟂ returned-content drift (LOW-MED).** If a processor returns fewer/renamed fields than the schema, the DuckDB projection must tolerate missing keys (null-fill) rather than throw mid-batch. Not specified.
8. **Cost-ceiling enforcement is advisory only (MEDIUM).** §10 records `requested×rate` but there's no hard pre-flight cap (exa clamps `max_credits` to a per-run ceiling worker-side, `exa_websets.ts:103`). Add a max-runs / max-USD guard the launch tool enforces before dispatch, not just a ledger estimate.
9. **HeartbeatLoop / observability (LOW).** `grep` shows **no HeartbeatLoop usage in core-x** pipelines; the precedents rely on the trigger waitpoint timeout (`"1h"`) + bounded Modal poll as the liveness mechanism. The plan does not need a new heartbeat, but for `ultra` (up to 2h) the waitpoint `timeout` must exceed the Modal poll budget, and the Modal poll budget must exceed the processor's worst-case latency — state both bounds explicitly (exa uses 50min poll < 60min fn timeout < 1h waitpoint; an ultra tier blows past all three).
10. **Basis-per-array-element beta header is opt-in (LOW).** If `industries_served__confidence` is wanted per element, the worker must send `parallel-beta: field-basis-2025-11-25`; otherwise basis is one entry for the whole array. The plan references Basis but not this header in the landing path.

## 4. Concrete recommendations (each tied to a file/section)

1. **Fix the topology claim and pick the idiomatic pattern (§3, §5.1, line 69).** Drop "poll group status from the trigger task via `wait.for`." Mirror the actual precedent: `src/trigger/parallel_task_enrich.ts` mints `wait.createToken({timeout})` and suspends on `wait.forToken`; `pipelines/parallel/task_enrich.py` does create-group → add-runs → **poll `GET /v1/tasks/groups/{id}` internally** (bounded budget, à la `exa_websets/ingest.py:614-630`) → `GET .../runs?include_output=true` → land → one flat callback. This is proven in-repo and removes the novel deviation. (If poll-via-`wait.for` is deliberately chosen for its zero-compute property, say so explicitly and own it as a *new* pattern — do not claim it mirrors exa.)
2. **Define the website input mapping (§3, §5.1) + null-domain skip (gap 2).** In the trigger/worker, build `company_website = 'https://' || normalized_domain`; pre-filter rows where `normalized_domain IS NULL`; record skipped count in `ops.parallel_runs`.
3. **Harden `refresh_catalog()` (§4.2, §6).** Have it also clear `catalog._lance_cache` and `catalog._schema_cache` (add a `catalog.invalidate()` and call it from the tool). Without this the §4.2 promise breaks on a pre-landing probe and `list_datasets` shows no `column_count`. Keep the opportunistic refresh-on-miss as the safety net.
4. **Correct the secrets section (§8, §9-phase-0).** `PARALLEL_API_KEY` already exists in `core-x/prd` — delete that provisioning step. Keep "create Modal secret `parallel-api`" (genuinely absent). Verify the gtm-mcp **service** sets `TRIGGER_SECRET_KEY` (Doppler holds `TRIGGER_SHARED_SECRET`; `hydration.py:69` reads `TRIGGER_SECRET_KEY`).
5. **Add idempotency + cost cap to the launch tools (§6, §10).** `launch_parallel_task_enrich` passes an `idempotencyKey` (e.g. `f"{spec_id}:{audience_id}:{run_kind}"`) and enforces a hard `max_runs`/`max_usd` pre-dispatch guard (clamp like `exa_websets.ts:103`), not just a ledger estimate.
6. **Specify array/nested schema→Lance mapping + drift tolerance (§4.1, new `pipelines/parallel/task_enrich.py`).** Document: `array<T>` → Lance `LIST<T>`; `_basis` → `STRUCT`/JSON; `<field>__confidence` derived from `basis[i].confidence` matched by `field` name; missing-key null-fill so a partial processor response can't abort the batch (precedent: `ca_cslb` `LIST<STRUCT>` projection).
7. **Define partial-failure + re-run semantics (§4.1, §10).** Land completed rows via `merge_insert`; persist failed `company_id`s; make a re-run resolve only missing/failed keys (the audience SQL ⋈ existing spec dataset, anti-join).
8. **Fix two factual nits (§6, §10).** `ultra` is ~20 fields (not ~25; ultra2x+ reach ~25). Re-word the §10 confidence-coverage rationale: the live basis guide says all processors return confidence — keep the conservative "verify per processor, land-and-flag" behavior but don't assert lite/base omit it as fact.
9. **State the timeout-bound chain for `ultra` explicitly (§9 deferred, §10).** waitpoint `timeout` > Modal fn `timeout` > Modal poll budget > processor worst-case latency. For `ultra8x` (up to 2h) this exceeds the exa-pattern's 1h ceilings — that, not "latency," is the real reason webhooks (per-run waitpoint tokens) belong in v1 for the `ultra` family. Re-scope the deferred webhook as per-run (groups have no webhook).
