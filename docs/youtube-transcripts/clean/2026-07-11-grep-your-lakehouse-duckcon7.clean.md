Why would you do that? Well, when you are building a lakehouse, when we are using a lakehouse, you have all the data already there. And I'm not sure if you have been there, but I've done that so many times. You want to synchronize a database with a search engine, because the database knows to do something and the search engine knows to do something else. That pipeline, a nightmare. I hated it. And I think we have seen that often times in the data world. What we wanted to do for Alter Table is bringing a new way, a new retrieval mode to our lakehouse, so that we could rely on the same storage layer than DuckLake, that DuckLake already uses, for search and semantic search.

Maybe a few reminders, because maybe not everyone is used to what an index is and what search is. Well, you can imagine that search is the process — or indexing is the process — of converting some objects that you have as input into the reverse version of them. So, you split the text, you maybe normalize some of that, but then what you build in a search engine is this map, this very optimized data structure that maps and associates the words that were in the documents to their IDs. You do that because then at query time doing a full-text search is very efficient. You very easily get to the inverted list of document IDs, and querying two words, and doing an AND between those two words, is just an intersection.

Something very similar is happening with semantic search. Instead of tokenization and simple normalization, it goes a little bit further with what most probably all heard about: word embeddings. So, we're basically creating vectors that are reflecting the content of the documents. And again, the indexing part of semantic search is about building this highly optimized data structure to be efficient for the search. We have chosen one simple graph structure, but it's really about putting all of that in the graph so that at query time you do the same: you do the embeddings on the query, you have a vector, and then with this very optimized graph you are able to search all the objects that have some similarity, some semantic similarity.

Well, let's go now to how we have been extending DuckDB. We have been very inspired by what the team has done a few years ago with DuckDB. I believe one of the key assets, and one of the extraordinary powers of DuckDB, is its extension system. And we have seen it in the ecosystem. For us, it was kind of obvious that we needed the extension system in DuckDB. And so, we have been building extensions on an extension. And by the way, we haven't started from scratch. We have been using a bunch of other open-source technologies. And shout out to Tantivy, that has been delivering amazingly so far.

A wise man told us once: "It's all just SQL." And so, this is definitely what we wanted to do with our approach, saying, "Okay, how do we start by extending DuckDB's SQL surface?" Of course, if we speak about index, well, the database world is coming with what we all know about indices, usually B-trees, usually in a transactional database, or in a non-lake database.

So, for us, it was obvious that we had to implement `CREATE INDEX` for DuckDB using either a full-text search index or a semantic search index, but something very similar. We're all very lazy, so generally we prefer the operators. We have been plugging the double-at operator that is already used by some engines for full-text search.

But usually, that's not enough. What you want is the scoring. I'm sure you have all typed into Google and stopped at the first result, because the first result is the most relevant. You don't scroll anymore — if you're still using Google. Here is the same. Every single time there is a search engine, every single time there is a search, whether it's a full-text or a semantic search, you have a score. A score, whether this reflects the relevancy. And the good thing with DuckDB, it has this virtual column mechanism that we have been using in order to reflect the score of what the search results look like.

Where it starts to be interesting is that instead of searching into the message column, I'm actually extending the DuckDB SQL dialect to allow anyone to use star as the column. And so this is where the magic happens. At this point, you are searching across all columns. Now that we had the SQL surface, we were like, "Okay, now it's time to implement." And again, one wise man once told us this. And it's something we really thought about when we were designing this extension. You probably know how DuckLake is working, but I'm going to still repeat it a bit. The lake is mostly a catalog and some Parquet files. Usually, you store them on a distributed storage, and we are using Postgres for now for the catalog. And one thing you can very quickly imagine is that adding search to DuckDB consists in bringing some of those small indices, those optimized data structures that we have built previously, very close to the Parquet files. So that it fits very nicely with all the snapshotting system, with all the time-travel system that the lakehouse is bringing.

Of course, under the hood, we had to also play a little bit with the metadata. We have been adding a few metadata tables in order to understand what are the indices that are created, what are the files, where are the files. So, the Tantivy index that we use for search actually relies on the file system from DuckDB, and a lot of things happening like that.

At query time, we have done a bunch of things — and this is of course a very simplified version of what we do — but we basically try to rewrite the query in a way that will be efficient for DuckDB to scan the table, scan the Parquet files, based on what the search results have retrieved. And so, as you might have understood, the DuckDB vector-search or the DuckDB full-text-search functions are returning row IDs and scores, and then well, it's all just SQL.
