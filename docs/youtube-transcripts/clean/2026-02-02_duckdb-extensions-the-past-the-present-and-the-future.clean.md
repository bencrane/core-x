So now, why have DuckDB extensions at all? Well, that's a great question, and I will answer it for us in this case. So there could be many reasons, and for us it boils down to — well, I think these four are quite key. There are also a bunch of others that I won't bore you with. One of the main things is that we care a lot about binary size. DuckDB is an embedded database and we want it to run everywhere, anywhere, which means that if the binary is 3 GB, that's a problem, because we also want to run in like storage-restricted or memory-restricted environments. So the binary size really matters. And DuckDB also wants to have an extensive feature set, and those things don't combine, so you'll have to make compromises. And through extensions we can actually select — or users can determine — what this trade-off is between feature set and binary size.

Another good reason is that we don't want external dependencies. If you've seen any talks about DuckDB before, you're probably familiar with the statement that DuckDB is a zero-dependency system, and that is true. But we do actually want to have dependencies, because there are many great libraries out there that we want to use. So what the solution here is, is to push them into extensions. So DuckDB itself remains fully dependency-free, whereas you have extensions which actually leverage these dependencies to implement certain features. But then only if you want to be exposed to these features, or if you need these features, only then will you actually be exposed to the external dependencies.

Then there are some other reasons why we want them. For example, functional incompatibility, where you would have extensions like — let's say you have different SQL dialects that are functionally incompatible from each other. Then extensions are a great mechanism to deal with that, essentially. And finally, we also have different maintainers for different parts of the code. So different people can maintain code that runs in DuckDB. We'll see how that works later.

Well, let's first take a step back and look at some challenges here, because as I've said, we have this unstable C++ API thing going on. So our main recommended extension template, describing how we recommend to build extensions right now, uses an unstable C++ API. Well, what does that mean? Well, it means that the API can change every version. It means you cannot rely on functions in this API to be the same next release. And what this means in practice is that you get some downsides. You get some downsides because, since this API is unstable, for example, we have to rebuild all extensions for every DuckDB release, which is kind of a burden. But not only that, it's also quite heavy on extension maintenance, because all the extensions also need to be updated whenever these APIs change. So every time a DuckDB core engineer changes an API which a lot of extensions use, it breaks a lot of extensions. All these extension maintainers need to be like, ah, what changed? And they'll need to fix it, which is work, and it's not ideal, of course. And finally, it's also hard to document, as well. The API is a very moving target, and that's on purpose — like, we want DuckDB to be able to move fast. Now the question is, is there a solution? Well, yes, we're working on one, which is also where the other templates come in. So the solution is to use a stable API, which you probably could have guessed. And what does this stable API bring? Well, stability. It means that when you compile an extension for DuckDB, it will actually just keep working, because DuckDB will say like, well, this API is going to stay the same for multiple versions, ideally forever, or until we decide that the thing becomes unwieldy. But this will allow extension maintainers to just build an extension and kind of forget about it, and it will just keep working, which essentially solves all these three main issues.

So that brings us to the goals. And the goals here are all focused on this stable C extension API, and switching actually the default from this unstable C++ API to the C extension API that is stable. So our main goals are to just expand this C extension API as much as we can. But there's more work to be done, and it's going to be one of our main priorities in this space. So with that being done, we want to also stabilize both the Rust extension template and the C extension template, leveraging the fact that these APIs will become more and more powerful, giving the community as well, but also the DuckDB Labs core team, the ability to leverage this stable API. Then finally, yeah, we want to migrate as many extensions over as possible, essentially, where we also want to see which ones we can actually move over to Rust and which ones we can move over to C or C++.

Okay, so the takeaways for today. DuckDB has a quite extensive extension ecosystem. It's being downloaded quite a lot.
