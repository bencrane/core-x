So I want to give a quick rundown of some of the features that we're planning for 2.0. It's always hard to make these slides because we're doing a lot of stuff, and we don't want to — it's always a bit of a fight of what's getting in, and we don't want to discredit — we have a lot of people working on DuckDB now, our cool team who's around, and you can chat with if you see this logo, the company logo. So one of the things that I want to talk about is the variant type. This is something that's actually already in DuckDB v1.5. And the way you can envision the variant is that it is kind of like JSON on steroids. It's like, imagine if JSON were fast. I think that's kind of the recollection. So basically variant type, it behaves very much similar to JSON in the sense that you can store data in any sort of row. The cool thing about variant is that it's no longer just a text-based thing. So DuckDB will automatically look at the schema that's in the JSON and then can try to extract common patterns, because often JSON does have some form of structure, extract that and then do optimizations on that, both at the storage layer so that it gets compressed and stored efficiently, and also at the query-execution layer so that you actually get very cool performance. And this is kind of how this looks like.

One of the plans we're also having, but we probably won't make for 2.0, but don't hold my words to it, is that we want to replace the actual JSON type with variant in the back end, so that you will get all these advantages also just when you keep on using the regular JSON type. And I think one of the nicer things about the variant as well, when it relates to this client-server, is that it actually works very well with these long-running log-collection things. Because there, what you often see is that you get a stream of logs in some JSON unstructured format, and you kind of have to keep them as JSON because they come from different sources, maybe they get different updates at different times, the schema changes, but they are very structured. And the cool thing about the variant is that you can now do this kind of real-time log ingestion into DuckDB while still getting a lot of the benefits of the engine, which the JSON type currently in its current state does not offer you. And so, as I mentioned, it's already in DuckDB v1.5, so you can already try it out, but it is going to get a lot of improvements in 2.0 that we're working on. So that's very exciting.

The other thing I want to talk about is triggers. So triggers — basically what a trigger is in SQL, is it is like an event sort of thing. You can basically say, if something happens in the system, you can now trigger another event. So one of the very common use cases of triggers is they have like audit tables or logs. So you can say, for example, "I want to create a trigger that after I insert into this table, I'm going to insert into my audit table." And it's also kind of something that works very nicely with this sort of long-running service. And we're planning to use this for a lot of other cool features that we're going to build internally as well. But it is also being exposed at the SQL level, so you can make your own cool triggers, do your own kind of cool stuff with this.

All right, object stores. Yeah, so object stores, that's one of the things that a lot of people use, like S3 or things like that. And it's often a central part of the DuckDB experience is interacting with object stores. I mean, in the end you have to get your data from somewhere. Usually DuckDB is not your source of truth for data, although that might change with the whole client-server thing, of course. But usually often these files are stored in these object stores. Of course, DuckDB has been able to read these object stores for a long time. For a long time we've been able to parallelize them. We can do a lot of cool stuff. But there have been some limitations when it comes to the synchronous file reads, which could then limit how fast we can read from these object stores. There were some workarounds, but it's not — it was never quite as nice. One of the cool features that's coming to DuckDB 2.0 is we're going to do asynchronous IO. And what that means in essence is that you can scale your IO layer, your input layer, separately from your query-processing layer. Which means that you can use a lot more parallelism for these remote reads, and that will make all this IO stuff, all this remote network stuff, a lot faster. We're planning it first for Parquet files, but it's also coming to other file formats, and also coming to the DuckDB file format, of course. And it will also help a little bit probably with local storage, but this is really — the network storage is going to be where you see most of the big gains.

Another cool thing that we're working on is partition-aware execution. So DuckDB itself in its native storage format doesn't really support partitioning, although there's some semblance of partition awareness you can use there as well. But the lakehouse formats like DuckLake, like Iceberg, and of course just having Parquet files on S3, they support partitioning, and it's often quite critical to get optimal performance to basically make partitioning-aware plans during query time. So one of the things we're also working on there is to make the query planning and optimization more partitioning-aware, which allows you to do a lot faster query processing on partitioned data sets and take full advantage of the partitioning.

Some changes that are more under the hood about DuckDB as well. So one of the cool things we're working on is the C++ V2. So if that doesn't ring any bells, then you may not have been working on the extension API or things like that. I will kind of summarize it for the main user-facing angle of this. So DuckDB has these extensions. And these extensions, they are very cool. They enable a lot of cool new features. However, currently the extensions are almost always made against the unstable C++ API, including our own extensions. And that gives a bunch of problems. If you develop an extension, you polish an extension, you have to choose a DuckDB version to target it to. So you have to build your extension for DuckDB 1.5.4. And then if the new DuckDB version comes out, you have to do it again. And because it's an unstable API, you have to constantly update your extension, keep it up to date. It's a lot of work. And that's something that we want to avoid. It's also something that for the community we have seen that if you rely on a community extension, for example, that may not be there for the next DuckDB release because of this, because the author has to actively work on keeping it up-to-date. So one of the things that we're working on is basically making the scope of our stable API much broader, so that we can develop these extensions, write them only once, build them only once, publish them only once, and then it will be available essentially until the end of time. That will both make life easier for extension developers, it will make life easier for us, but also it will make these extensions a lot more reliable for the community, because they're not going to just disappear on you. Also, nowadays it's of course much easier to build these extensions if you want to have a go at it, with all the AI tooling and stuff. So maybe once this hits, give it a go. You can do a lot of cool stuff with these extensions, and it's all constrained. You can make DuckDB do a lot of cool stuff. Yeah, that's the C API for extensions indeed.

Another cool thing that we're working on is we're ripping out the old parser and we're making a new parser. So DuckDB has famously always used the Postgres parser. And we have basically decided enough is enough. We are going to make our own modern parser. That kind of ties into the extensions as well, and allows the extensions to integrate new parser constructs much more easily.
