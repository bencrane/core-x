Okay, I have to admit that when I saw the lineup I nearly decided to cancel, because I used to work with Josh for four years at Cloudera and always hated going after him. Todd, before Julia details talk, encouraging me to keep going, because once upon a time I was one of the early co-authors of the pandas library, so I'm glad to hear the kind words here.

Now I'm working on Lance columnar format and LanceDB. So I think Lloyd — what Lloyd's talk was, the furthest back in time — Josh's talk was certainly the funniest. I'm going to claim to have the craziest talk, about how to build a full AI tooling stack using DuckDB, or how to bring that into the DuckDB system. So just picture me as the *It's Always Sunny* conspiracy theory theme, the meme.

So the problem that I've seen with ML and MLOps and AI is that it's not just that your data is not rectangular, but the data is really irregular. So you have annotations and labels and bounding boxes, and you have lots of deeply nested data, and then you also have really large blobs that can get up to dozens of megabytes or sometimes even gigabytes when you have 3D scans of things. And so what ends up happening in data lakes for AI-heavy shops is you have your single source of truth format that might be Parquet or something, but then you have another copy of that data that stores like TFRecords for training, and then you have yet another copy for debugging or evals or some other thing. And so this creates a lot of complexity for tooling, the pipelines that you build on top of it. It also really blows up the cost of data storage and compute.

So that's all we try to solve with Lance columnar format, which we're working on with the LanceDB team. So it's a high-performance new columnar format optimized for AI. It's designed to unify storage across embeddings, text, metadata, tabular data, images — everything that you can think of. Out of the box it's compatible with our favorite tools like DuckDB and pandas, Polars, PyTorch, and more. It comes with zero-copy schema evolution and versioning, so you can always roll back to the previous good state if your model eval shows bad results. And because of the optimizations we've done in the data format, we can achieve several orders of magnitude faster performance than Parquet in terms of random access, and just reduce overall training time by at least two to three times with faster shuffling, with faster filtering, and just faster data loading.

All right, but the data format itself is not enough to have a full-fledged AI tooling chain in DuckDB. So you need the models to run in SQL, you want UDFs, and you want data exploration tools. So what you need is a data layer that is hopefully Lance format, then you need DuckDB extensions for PyTorch or TensorFlow, and you need scanners for specialized data — like if you use FFmpeg or OpenCV to build a frame scanner for videos. And then you can add UDFs on top of that to do image transformations like crop and rotation. Of course, all of those you can plug in with CUDA integration, and all that is possible because DuckDB is written in C++ and it works with all of those tools. I had a tool to do all that, put all that together, in a blog post called "Peking Duck" with two e's — so peeking, not really hosting.

The key to a successful business is location, location, location. I think the key to a successful data system is types, types, types. So Arrow and DuckDB types are maybe 80% interoperable. Unfortunately, right now AI sort of falls into that missing 20%. Those come in sort of three buckets. One is nested types, for like annotations, bounding boxes, labels. And then extension types, for images, embeddings, videos, point clouds, and things like that. And then there are some ML-specific types like bf16, but those should be fairly easy to add. And the problems are going to be how to make sure that all of these different layers agree with each other and can talk to each other.

Two other small problems: in the push-down layer, DuckDB pushes down to Arrow using the PyArrow compute expressions, but that's not a standard across different Arrow implementations. So if we're using like Lance format — uses Rust, for example, we use DataFusion to handle predicate push-downs — so there's some pain points there. Possibly Substrait can serve as a long-term interface, but who knows.
