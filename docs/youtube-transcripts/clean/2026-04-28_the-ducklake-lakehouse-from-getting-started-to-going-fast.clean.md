What inlining means is if I'm inserting small amounts of data, instead of writing a separate Parquet file every insert, I'm going to batch those up by putting those as rows in my catalog database first, and then later I will flush those rows out of my catalog database into larger Parquet files. However, things don't disappear when they go into that catalog database. All of your read queries will still be able to read out of that catalog, and it'll still be completely transactionally sound. So sort of like you get the buffering type of capability of a Kafka, but you keep the transactionality of a lakehouse. It really is a significant simplification over having to run Kafka, and a significant performance boost over having tons and tons of tiny little files. So what this practically means is that you can ingest much more often into DuckDB than in other formats. Multiple times per second, which will be significantly better.

So if you want to insert in bulk, we will typically be skipping the inlining step. We'll be going straight to Parquet. So how do I optimize for that bulk workload that's a little more common in traditional lakehouse scenarios? The first thing is I'd recommend enabling per-thread output. What does this mean? It means that each DuckDB thread is going to write its own Parquet file, which allows us to blast data at object storage a lot faster. It doesn't make us synchronize things across threads. We could just push the data as fast as we can. There's a trade-off here. You're going to have more Parquet files. And so what that means is you might want to run your compaction a little bit more often. And often that trade-off is worth it. The next thing, if you're frequently loading data in bulk, I would recommend lowering the default retry wait time in DuckDB. And that means that your catalog is going to be able to move faster. So the way that DuckDB handles transactionality, it does optimistic concurrency control like all the other lakehouses do, where it will by default try and write your data, and then it will force a retry if there's some reason that it's not valid to commit, like let's say someone else got there first. And typically it waits 100 milliseconds before trying that retry. And for most lakehouses, that could be a while, but for a transactional database, that's a long time. So you can shrink that number way down and insert data more quickly. So that is kind of the fast-ingest workload.

Another common workload that you want to tune for is on the opposite end of the spectrum: how fast can you read data back out of your lakehouse. The key way to do this is to read as little data as possible. We saw a bit of that in the demo. And DuckDB does that at two layers. The first layer is what we looked at, file-level statistics stored in the catalog. So when you read data out of DuckDB, step one, talk to the catalog. What files do I want to look at? And then step two is go grab those files or pieces of those files. So we want to make sure that list is as small as possible by keeping the statistics as narrow of a range as possible for the things you're filtering on. One key thing to look at there is partitioning. We'll see that in the next couple slides.

Now the second level of filtering is once you've decided what files to read, I don't want to read the whole file. So DuckDB and any other DuckDB reader are just going to read just the columns that you want, and just the row-group chunks. So Parquet files are split up into chunks, and we only want to read the chunks that match our filters. And the way to improve this and tune this is with sorting, which other folks call clustering. Same approach. DuckDB has that capability.

So if you want to reduce the number of files that you read in total, you may want to partition your data. Frequently, you can partition by time buckets, year-month-day, or you might partition by something that's domain-specific. Maybe you're always querying by customer. Maybe you want to split out your data by customer to make sure you only read exactly what you care about. But what if you have a million customers? I would not recommend creating a million partitions, because those files will be tiny, and you'll spend so much time deciding what to read that you might as well just read a little bit of extra data. And so there's a tuning knob here that is a Goldilocks approach called bucket partitioning. This is also something supported by the other lakehouses, where I can say, hey, make a thousand buckets of customers. So if you know which bucket to go to, like for one specific customer, you did save a thousand times the amount of data you're reading, but maybe you won't have too many small files that way. So that's a number that's worth tuning. Somewhere in the hundreds to thousands is probably a good partition count to have. I don't know if I'd recommend hundreds of thousands of partitions, for example. So there are things to be careful of. Partitioning does take more work on the ingest side, and you can end up with more small files. So those are the other side of the coin. Be careful while you tune it. But by default, hundreds of partitions, probably a pretty safe sweet spot.

The next level of tuning is with clustering or sorting. And the idea is to read as few pieces of Parquet files as you can. So you can imagine, in that demo, I had a column that was totally random. I'm going to have to read all the rows in my data to decide what J values I want to grab, because it was randomly distributed. But if I sort my data, I could pick only one row group out of a file. And I tend to aim for a rule of thumb of about 10 row groups per file, plus or minus. So that means that if you sort correctly, you get a 10x boost. And that can be huge. So somewhere around 10 row groups per file is probably what I recommend. That works out pretty well with that like 80 MB example we had before. That means each file is close to a gigabyte. That's a pretty good file size for a lakehouse format, somewhere around that gigabyte to half-a-gigabyte range for each file. The syntax for this is set sorted by, and you can set any expression or set of expressions. So you can sort by customer then by date, or date then by customer, or any other combination. And I'm very biased. This is my main contribution to DuckDB so far, is this sorting capability. So I added this index, and I'm really a big fan, and I think it'll come in really handy.
