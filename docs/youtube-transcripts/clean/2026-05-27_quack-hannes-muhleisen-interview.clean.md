So, Jose: what are some of the things, if any, that had to fundamentally change with DuckDB in order to be able to now handle concurrent reads and writes? So, that's a great question. DuckDB itself always has been able to handle concurrent reads and writes. However, you had to be in the same process. And there were some restrictions. For example, we couldn't handle concurrent writes while a checkpoint is running. So, for those of you who don't know what a checkpoint is — the way database fault tolerance traditionally works is, the changes that you made are written to a journal file called a write-ahead log. They are always forced to disk, and then if a crash happens, the database file can basically be recovered and made consistent to the last committed state, by reading this journal file. That kind of avoids you having to rewrite the database file every single time you commit, which is, by the way, what SQLite does. It's not efficient. So, DuckDB has had this thing where — and sorry, checkpointing is the process of basically eventually cleaning up that journal file, because you don't want that journal file to grow till the end of time. So at some point you have to fold all the changes that are on the journal back into the main database file — that's called checkpoint. We used to have this restriction that we couldn't commit while checkpointing, but Mark has recently worked on this, and now DuckDB can do it. So the in-process version of DuckDB has for a long time been capable of these things; we have improved it recently. But otherwise, for Quack to work, nothing really fundamentally had to change in DuckDB. In fact, I don't think I committed any change to DuckDB as part of the implementation of Quack.
