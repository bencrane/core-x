DuckDB just released what they call their next big thing, which is a client-server protocol for DuckDB called Quack. And in this video, I'm going to explain what it's all about, how Quack works, and where actually MotherDuck sits after this release. Just giving my honest take, taking it with a grain of salt. You're watching this from the MotherDuck channel. And see how it could be useful for you.

So, quick recap. DuckDB is a new kind of database. Typically, you have in-process and client-server databases. And the two big categories are transactional and analytical. And historically, we have for analytical databases a heavy server side where all the cloud compute is done and a light client where basically it's just SQL sent over the wire. Snowflake, BigQuery, and others are all into that setup of client-server. DuckDB, when it appeared in 2019, kind of flipped the story where it says: SQLite is for transactional, here we have a new kind of category of database for in-process analytics.

Well, our hardware today is much more powerful than it used to be. So why do we need a heavy cloud setup when the client could actually process a lot of data? And if you've been using DuckDB a lot, you've probably been eating some of those challenges where, if you want multiple writers — so you have multiple DuckDB processes writing to the same DuckDB file — you cannot do that because the file is locked. Another big use case is that if you need to share a large DuckDB file for read-only purposes, well, users will have to download it somehow, or you need to have your compute really close to the storage to be efficient. Typically, for BI use cases — so where you have a BI tool connected to a SQL engine — that's one of the big challenges that DuckDB in the current setup can't really solve out of the box.

So, let's dive into what Quack actually is. So, Quack is a DuckDB extension. So, like any DuckDB extension, you just do an install and load the extension. Because it's currently in preview, it will be GA'd by DuckDB 2.0, which is announced later this fall — you have to specifically install Quack from core nightly.

Let's say you have one DuckDB as a server and one DuckDB as a client. And so, that's the other big thing: any DuckDB process can play the role of a client or server, or both. So, once you have installed the extension on both sides, you load it, and then on one side it's going to play the server: you call the Quack serve, and now you have a server with a token. On the other side, the only thing you need to do is create the secrets, and then you can attach the database like it would for any other regular database, pointing to the URL and alias.

So, the protocol is using HTTP/2. I'm not going into the details of why they've put that in — their blog goes deeply into why they pick HTTP/2. With any protocol, there is some trade-off, of course. But one of the big pros here is that because DuckDB also works in WASM, you can basically have the client in a browser tab connected to a remote server. So, once you attach, you have your alias, and it's really just like you would query a local DuckDB database. Here you see the remote alias, and the query is sent over the network, computed on the server, and then you get the result back.

All right, so what does it solve? I already spoiled you: many writers with one server, that's really obvious and one of the big limiters that this setup of client-server lifts. The other thing, as we talked about, if you have many read clients that point to a specific large DuckDB file, typically BI tools or other stuff, that's also another big one. And the latest I just mentioned, which is basically with DuckDB WASM acting as a client and you can connect to a bigger machine on the cloud where you have your DuckDB server hosted.

Also worth mentioning, coming soon, is the DuckLake catalog coming on DuckDB. So today if you want to run DuckLake in production, the recommendation is to go Postgres for the specific limitation of multi-writer, and that will be lifted with using the Quack protocol, so there is a work-in-progress PR on that.

So where does that leave MotherDuck now? I think before talking about MotherDuck itself, we have to understand what a data platform, a data stack, is. The protocol here, the client-server, is just one tip of the iceberg, it's just one layer. So you also have to think about authentication, SSO, users — there is no concept of users in DuckDB — authorization, and also security. By default, the server provides HTTP, so you're on your own to set up your own web proxy, web server, and so on. And then there is everything related to the compute itself: even if you have remote compute, how do you manage failover, always up, scale up, scale down, all that jazz. So that's really classic for a data platform.

And then for sure, here it's not a MotherDuck pitch, but there are specific features of MotherDuck, not just this one of dual execution — probably worth mentioning on this client-server protocol — but we have the SSO and other stuff that is just right above. But it's just to let you think about what you need and what you want to build. And at the end of the day, this is really always the same question: build versus buy. If you are a small team who likes operational simplicity and that's fine, then sure, go ahead and build this and use this protocol. But if you can't afford to spend time on this, then you will use managed services, of course, like everyone does for other things than just data.

In any case, we are super excited about this feature. MotherDuck has been building its own protocol to enable this for years now. It is great that, as we have pushed the boundaries of DuckDB in the cloud in client-server mode, DuckDB Labs is also coming with its own standard for the DuckDB ecosystem. So I'm really curious personally about what people are going to build. I think there's going to be a lot of creative stuff, and at least we are cooking.
